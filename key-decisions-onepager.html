Internal Tools: Build vs Buy — the key decisions

Series C fintech · 60 engineers · $250k/yr Microsoft spend (composition unknown — license audit OPEN) · 3 Power Apps live (KYC queue, refunds dashboard, flag panel) · 10 more planned · Pilot built + measured · Oct 2026
Recommendation: not build-vs-buy — route. Power Apps keeps forms/approvals on M365 data (analyst-maintained, ~zero engineering). Devin-built lane owns queues, consoles, and anything needing engineering-grade guarantees (audit envelopes, field-level encryption, perf budgets). Power BI owns scheduled reporting. Solved commodities are bought. Every net-new tool enters as a one-page press release and is routed by the Intake Gate — the promises become the acceptance tests and the quarterly KPIs.

What the pilot proved (measured, not asserted)

KYC queue p95: 10.3ms @ 50 rps / 10k cases — 97× under the 1s promise 100% decisions audited — same-transaction, enforced by test PII masked by default; reveal is an audited, role-gated event Flags eval API p95: 0.7ms vs 50ms budget Rate limiter under 2.76M-req flood: 97.3% throttled, 0 5xx Review turnaround stayed well under the 48h D4 gate all pilot Full VP demo arc rehearsed in 3m19s (budget 20m) New app from template: cp -r _template, green with zero edits
  • Cost shape: at 100 users, PA Premium ≈ $24k/yr forever vs Devin-built ≈ $4–12.5k one-time + ~$6k/yr run+review [EST]. Cost decides only at the extremes — many users → Devin lane; zero engineering availability → PA by default.
  • Honesty on record: the ACU-cost metric line was withdrawn when session counters proved unavailable — no number emitted rather than a fake one. Friction log: 11 entries, all published.

What Power Apps genuinely wins (steelmanned)

  • Governance is a console, not a program — DLP, Managed Environments, audit, FedRAMP High GA: toggle-on, pre-audited.
  • Analyst maintainability — retune a form in hours, unassisted. Devin-lane change = PR + review. Structural, not a maturity gap.
  • M365/D365 gravity + bundled economics — M365-seeded rights can make a forms app ~$0 marginal.
  • Vendor permanence + the platform's future included in the license.

Where the risk lies (both directions)

  • Devin lane: review capacity is the real currency (D4 exists because of this); 33% of agent PRs don't merge (vendor-reported); mid-task scope change is its documented failure mode; vendor is a 3-year-old startup — mitigated by full portability (our Git, DBs, CI; exit reserve).
  • PA lane: per-seat math at scale; premium-connector traps + delegation limits on queues; engineering consoles frustrate engineers. Both vendors repriced within 6 months of each other — neither is a pricing safe harbor.

What would reverse this recommendation (pre-committed falsifiers)

  • Review turnaround sustains >48h → Devin lane shrinks to consoles-only; queues re-route to Power Apps.
  • License audit shows Premium sunk + incoming requests skew forms-heavy → PA-primary; Devin stays pure engineering productivity.
  • RefundLens usage logs: filters used, ask-box ignored (4-week evidence gate) → kill conversational layer; reporting consolidates in Power BI.
  • Flags trigger fires (replica shows clear capability/run-cost advantage and audit shows Premium growth — both, not either) → migrate flags to the Devin-built exit design, accepting SDK + 99.95%-SLA ownership as the honest cost.
  • ACU/app >3× estimate for a quarter → renegotiate the order form or cap lane intake.

Where Devin fits — on either path

  • If routed portfolio approved: Devin is the build plane for the Devin lane — apps #2+ ride the platform packages (auth/audit/crypto/ui/testing), so marginal build cost falls; the weekly KEEPER session owns dependency and backup-restore upkeep; the flags SDK-wave migration (if triggered) fans out managed Devins, one PR per service repo.
  • If the answer is "stay mostly on Power Apps": Devin still earned its place this pilot — the replica priced what flags ownership would cost (the reason to stay put), and the lane remains the escape hatch for any app that outgrows the platform.
